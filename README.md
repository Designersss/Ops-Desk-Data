# Петро Билдинг Системс · PBS

Веб-система учёта производственных данных и управленческой аналитики. **Next.js 16 · TypeScript · SCSS · PostgreSQL.**

Сотрудники трёх участков вносят и исправляют данные прямо на сайте. Директор видит сводные KPI, графики, ошибки и связанные записи, выбирает период и скачивает CSV-отчёт. Все расчёты и доступ к данным выполняются на сервере. Открытые страницы обновляют данные из PostgreSQL примерно раз в 8 секунд, поэтому изменения другого сотрудника появляются без ручной перезагрузки. **Excel-файлы после первоначального импорта не нужны.**

## Запуск локально

Понадобятся Node.js 22+, [pnpm 10](https://pnpm.io/installation) и Docker Desktop (либо работающий PostgreSQL 17+).

```bash
git clone https://github.com/Designersss/Ops-Desk-Data.git
cd Ops-Desk-Data
corepack enable
corepack prepare pnpm@10.21.0 --activate
pnpm install
# Создать .env только при первом запуске — не перезаписывать действующие настройки.
test -f .env || cp .env.example .env
# Убедитесь, что Docker Desktop запущен.
docker compose up -d
docker compose ps
pnpm db:migrate
pnpm db:seed
pnpm dev
```

Откройте **http://localhost:3000**. `pnpm db:seed` загружает 23 исходные учебные строки **только в пустую базу**. Если данные уже есть, ничего не перезаписывает. При последующих запусках достаточно `docker compose up -d` и `pnpm dev`.

В файле `.env` укажите актуальный `DATABASE_URL` при использовании внешнего PostgreSQL; `.env` не нужно коммитить.

Для производственного запуска: `pnpm build && pnpm start`. Предварительно настройте миграции, БД и переменные окружения.


### Если данные не загружаются (PostgreSQL)

При ошибке сайта «Не удалось загрузить данные» сначала посмотрите **терминал, в котором запущен Next.js**, и статус базы:

```bash
docker compose ps
docker compose logs --tail=40 postgres
```

В локальной установке проекта PostgreSQL открывается на **127.0.0.1:55432** (в контейнере используется 5432). Это намеренно позволяет работать рядом с другими установленными PostgreSQL, которые обычно занимают порт 5432.

Если вы запускали предыдущую версию проекта и файл **`.env` уже существует**, откройте его и замените:

```dotenv
DATABASE_URL=postgresql://pbs:pbs_local@127.0.0.1:55432/pbs
PBS_DB_PORT=55432
```

Изменять `.env.example` недостаточно: приложение читает существующий локальный `.env`. После этого выполните:

```bash
# Docker Desktop должен быть запущен
docker compose up -d --force-recreate postgres
docker compose ps
docker compose exec -T postgres pg_isready -U pbs -d pbs
pnpm db:migrate
pnpm db:seed
pnpm dev
```

При работающем PostgreSQL `docker compose ps` показывает контейнер как `Up (healthy)`, а `pg_isready` сообщает, что сервер принимает соединения. Если порт **55432** также занят, выберите свободный порт и укажите **одинаковое значение** в `PBS_DB_PORT` и в порте `DATABASE_URL`.

Ошибка `Bind ... port is already allocated` означает конфликт опубликованного порта на компьютере. Ошибка PostgreSQL `28P01 password authentication failed` часто означает, что `DATABASE_URL` указывает не на контейнер PBS, а на другой сервер с другими учётными данными.

**Не используйте `docker compose down -v`, `docker volume prune` или `pnpm db:reset` для устранения ошибки подключения:** это может удалить сохранённые данные. Если после смены порта возникает ошибка аутентификации, проверьте, какой контейнер работает, и содержимое `DATABASE_URL`, не публикуя пароль.

## Общие данные для разных устройств

**База данных размещается на сервере**, а не в браузере. Пример: Next.js на вашем сервере/хостинге и PostgreSQL с постоянным диском/управляемой базой. Все участники открывают один URL и работают с одной БД. Повторное открытие сайта, перезагрузка страницы или перезапуск Node.js не теряют изменения.

Для просмотра с телефона в одной домашней сети (локальная разработка) можно запустить `pnpm dev --hostname 0.0.0.0` и открыть `http://<LAN_IP_компьютера>:3000`. Оба устройства при этом обращаются к **одному серверу**; компьютер с PostgreSQL должен быть включён.

Для доступа через интернет нужен деплой Next.js и подключение к постоянному PostgreSQL. Сам репозиторий **не является публичным размещением сайта**.

## Разделы и роли

Роли выбираются внизу левого меню:

- **Директор:** Обзор (KPI, динамика, сводка с детализацией), все журналы и детали, качество данных, отчёты, настройки и импорт.
- **Сотрудник заготовки:** свой журнал, KPI и график заготовки, добавление и исправление записей.
- **Сотрудник сварки:** собственная потребность, обеспеченность, журнал и редактирование записей участка.
- **Сотрудник документации:** независимые KPI план/факт и собственный журнал.

При `NODE_ENV=production` обязательно установите `SESSION_SECRET` (случайная длинная строка) и четыре PIN: `DIRECTOR_PIN`, `PREPARATION_PIN`, `WELDING_PIN`, `DOCUMENTS_PIN`. При выборе роли появится запрос PIN. API проверяет подписанную HTTP-only cookie и разрешённый участок **на сервере**. Без PIN-параметров роли в production не открываются. В локальном `pnpm dev` для удобства переключение свободное. PIN подходит для задания, **не для настоящей корпоративной авторизации**; при эксплуатации с реальными данными необходима полноценная аутентификация, ограничения попыток входа, TLS и администрирование ролей.

## Импорт исходных Excel-файлов

1. Можно сразу работать с 23 учебными записями, созданными командой `pnpm db:seed`.
2. Чтобы проверить загрузку вручную, откройте **Настройки → Импорт данных** и выберите три `.xlsx` — по одному на каждый участок. Если в БД уже есть записи, требуется явное согласие на замену **всех** существующих данных.
3. Импорт проверяет колонки и данные и сохраняет все три набора **одной транзакцией**. Если один файл неверный, старые данные сохраняются без частичной замены.
4. После успешной загрузки можно удалить исходные Excel-файлы. В приложении хранятся строки и дата импорта, повторное обращение к Excel не требуется.

Ожидаемые имена колонок на листе `Данные`:

| Участок | Колонки |
|---|---|
| Заготовка | `record_id, date, batch_id, employee, plan_qty, fact_qty` |
| Потребность сварки | `record_id, date, batch_id, need_qty` |
| Документация | `record_id, date, employee, plan_docs, fact_docs` |

Импортирует сохранённые значения, а не исполняет формулы Excel. Размер каждого файла ограничен. Отсутствующий факт, дубликат или явно подозрительный факт сохраняются как исходные сведения и **отмечаются контролем качества**, а не скрываются исправлением при импорте. Поле «Сотрудник» в исходной сварке отсутствует, поэтому там стоит «Не указан»; сотрудника можно указать при добавлении/исправлении записи на сайте.

## Бизнес-правила и формулы

- **Заготовка:** подтверждённое выполнение = сумма проверенного факта / сумма плана **по тем же проверенным строкам** × 100%. Недостоверные строки не считаются подтверждёнными, а не заменяются нулём.
- **Связь между датами:** сварка за выбранный период может использовать заготовку той же партии, выполненную раньше. Проверка связи ведётся по полному набору записей, в итог периода попадают только заявки за выбранные даты.
- **Потребность сварки:** сумма `need_qty` по заявкам; партия связывается с заготовкой по `batch_id`. Обеспеченность вычисляется **только при однозначной и корректной связи**: покрытие = `min(факт заготовки, потребность)`, дефицит = `max(0, потребность − факт заготовки)`. Если есть дубль, отрицательный факт, пропуск или аномалия, обеспеченность **не определена**, даже если потребность известна.
- **Документация:** `sum(fact_docs)/sum(plan_docs) × 100%`, независимо от двух других участков.
- **Контроль:** дубли записей или партий, пустые факты, отрицательные значения, отсутствующий сотрудник, аномальный факт выше 300% плана и неверные планы/потребности. Порог 300% — демонстрационное правило проверки, **не универсальный производственный норматив**. Если в реальной работе превышение допустимо, требуется отдельный процесс подтверждения.
- Фильтр периода на «Обзоре» и в «Отчётах» применяется **на сервере** к выборке записей. Проблемы дубликатов проверяются по полному набору данных, чтобы границы периода не скрывали ошибки.

Контрольная проверка исходных значений: **5–6 октября 2026 года, заготовка 190 / 200 = 95%**. На полном исходном наборе: заготовка 290/400 = 72,5%, сварочная потребность 750 единиц, документация 18/26 = 69,23%, пять проблемных строк заготовки.

## Сценарий проверки работодателя

1. Открыть сайт под ролью «Директор», просмотреть сводные KPI и ошибки.
2. Зайти в «Качество данных» → **P-003** → «Редактировать запись», поменять `1200` на `120`, сохранить.
3. Проверить обновлённую заготовку **410 / 500 = 82%** и исправленную обеспеченность сварки для `LOT-03`; документация остаётся **18 / 26**.
4. Открыть детальные страницы и связанную заявку `W-003`.
5. В «Отчётах» скачать **CSV**; он содержит выбранный период, исходные строки, качественные статусы и расчётные величины.
6. Перезапустить сервер, снова открыть запись и убедиться, что факт **120** сохранился. Остановить или удалить Excel-файлы можно после первого импорта — данные останутся в PostgreSQL.
7. При желании проверить с другого устройства, открывая тот же сервер и ту же базу.

Чтобы восстановить исходные учебные записи для повторной проверки, выполните **только при явном намерении удалить все изменения**:

```bash
CONFIRM_RESET=YES pnpm db:reset
```

Это удалит изменённые/добавленные записи, заново запишет 23 исходные строки и сбросит журналы изменений.

## Тесты

```bash
pnpm typecheck
pnpm test
pnpm build
```

При работающем PostgreSQL интеграционные тесты: `INTEGRATION_TEST_DB=1 pnpm test`. **Внимание:** интеграционные тесты изменяют тестовую БД и восстанавливают начальный набор; **не направляйте их на рабочую БД!** В GitHub Actions поднимается отдельный сервис PostgreSQL для проверок.

Браузерные сценарии Playwright (нужен запущенный Next.js, отдельная тестовая база и Chromium):

```bash
pnpm exec playwright install chromium
pnpm test:e2e
```

Проверяются редактирование и пересчёт, CSV, перезагрузка, изоляция ролей, мобильный экран и повторный импорт. E2E-тест **заменяет данные тестовой БД**.

## Архитектура

```text
src/app/               Next.js App Router и серверные API-маршруты
src/components/        React-экраны и формы
src/styles/            SCSS + утверждённая PBS дизайн-система
src/lib/model.ts       Контракт данных, Zod-валидация
src/lib/analytics.ts   Проверка качества и серверные расчёты
src/lib/repository.ts  PostgreSQL CRUD, транзакции, версии, audit
src/lib/importer.ts    Безопасный разбор XLSX
src/lib/report.ts      CSV-отчёт с BOM и защитой от формул
db/schema.sql          Таблицы и индексы
scripts/               Миграции, первоначальный импорт, явный сброс
tests/                 Unit- и PostgreSQL-интеграционные тесты
e2e/                   Playwright-проверка пользовательских сценариев
public/assets/         Оригинальный логотип PBS
legacy/                Архив ранее согласованного HTML/CSS/JS-интерфейса
```

Устройство проекта предельно простое: React отвечает за отображение/формы, серверные маршруты — за проверку роли и входных данных, сервис анализа — за расчёты, репозиторий — за SQL и хранение. Никаких бизнес-формул в JSX, никакой зависимости от исходных файлов после импорта.

---

**Важное ограничение тестового проекта:** роли на PIN — это демонстрация разграничения рабочих экранов, а не полноценный промышленный IAM. Для реальных корпоративных данных потребуются SSO/учётные записи, разграничение прав по пользователям, контроль доступа к API, журналирование входов, резервное копирование и мониторинг PostgreSQL.
