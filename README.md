# Ops Desk — рабочее тестовое для Data/AI Analyst при CEO

Небольшая демоверсия единой операционной системы вместо трёх Excel-таблиц: **Заготовка**, **Потребность сварки**, **Документация** и общая панель руководителя.

## Быстрый запуск

Требуется только **Python 3.10+**. Никаких `pip install`, Docker, PostgreSQL, интернета и сторонних JS-библиотек.

```bash
git clone https://github.com/Designersss/Ops-Desk-Data.git
cd Ops-Desk-Data
python3 server.py
```

Откройте **http://127.0.0.1:8765**.

При первом запуске система **автоматически один раз импортирует все три учебных Excel-файла** из `examples/` в новую базу `data/app.db`. При следующих запусках файлы не нужны: можно их удалить, изменения сохраняются, повторный импорт при старте не происходит. Можно сразу открывать панель и исправлять записи. Для повторной демонстрации импорта файлы включены в `examples/`; загрузить их можно через вкладку **«Импорт Excel»**. Повторный импорт заменит текущие данные, поэтому сначала подтвердите действие.

## Сценарий показа (2–4 минуты)

1. Откройте панель директора, период **05.10.2026–14.10.2026**. На ней показаны 5 проблемных строк в заготовке и 4 непроверенных связи со сваркой.
2. Перейдите в **«Качество данных»**. Найдите `P-003`, факт **1200** при плане **100** — запись помечена как требующая проверки. Пока значение не исправлено, LOT-03 не участвует в подтверждённом расчёте обеспеченности сварки.
3. Откройте **«Заготовка»**, исправьте `P-003`: `fact_qty = 120`, сохраните. Вернитесь на панель директора. Теперь факт заготовки **410** (был 290); подтверждённые связи сварки — **5 партий** (было 4), её подтверждённый дефицит — **50** (был 40). Показатель документации **18 из 26** не изменился.
4. Откройте на панели **«Источники»** у `LOT-03` или **«Записи»** у даты 07.10.2026, проверьте прослеживаемость.
5. Нажмите **«Скачать отчёт»** — получите CSV с BOM UTF-8, пригодный для Excel, содержащий сводные показатели, первичные строки и качество связей.
6. Остановите сервер (`Ctrl+C`) и запустите снова. Исправление останется в SQLite. Можно также удалить все файлы `examples/*.xlsx` — приложение продолжит работать; исходные файлы больше нигде не читаются после импорта.

```text

  server.py            HTTP-сервер, SQLite, импорт XLSX, валидация, расчёты, CSV
  static/index.html    Оболочка интерфейса
```

## Бизнес-правила и формулы

**Связь:** строки «Заготовки» и «Потребности сварки» сопоставляются по `batch_id`. «Документация» не имеет подтверждённого общего ключа для связи с другими участками и остаётся независимой.

**Выполнение заготовки** = `SUM(fact_qty) / SUM(plan_qty)` по подтверждённым записям выбранного периода. В предоставленном файле контрольный пример за 05–06 октября: `190 / 200 = 95%`.

**Потребность сварки** = `SUM(need_qty)` по подтверждённым строкам сварочного участка. Этот показатель **не зависит** от качества данных заготовки.

**Связанное покрытие сварки**, только для партий с одной валидной записью сварки и одной валидной записью заготовки в периоде:

- `покрыто_по_партии = MIN(fact_qty, need_qty)`;
- `дефицит_по_партии = MAX(need_qty - fact_qty, 0)`;
- `обеспеченность = SUM(покрыто_по_партии) / SUM(need_qty по подтверждённым парам)`.

Пример на всех исходных строках: 4 проверенные партии из 8; потребность по ним = 320, покрыто = 280, дефицит = 40, обеспеченность = **87,5%**. **Нельзя трактовать 87,5% как обеспеченность всех восьми партий** — интерфейс специально показывает эту оговорку.

**Выполнение документации** = `SUM(fact_docs) / SUM(plan_docs)` по проверенным записям, независимо от предыдущих двух участков.

**Качество:** пустые обязательные поля, некорректные даты, повторный ID, повторная партия в одном участке, отрицательные или дробные количества, нулевой план, а также факт выше трёх планов помечаются. Правило **«выше 300%» — демонстрационная эвристика**, а не подтверждённое компанией ограничение: такую строку нужно проверить, а не автоматически менять. Проблемные строки исключаются из *подтверждённых* сумм; если входящая заготовка недостоверна, недостоверным помечается и **связанный** показатель сварки. Сварочная потребность и документация при этом сохраняют самостоятельную достоверность.

Допустимы исправление, создание и удаление строк. При удалении одного из двух дублей `P-005` оставшаяся запись перестаёт быть дублем и автоматически вновь участвует в расчёте.

## Ограничения демоверсии

- Это учебное приложение без авторизации, разграничения ролей и интеграций с ERP/1С/Битрикс. Разделы интерфейса разделены по рабочим процессам.
- Загрузка поддерживает предоставленную схему `.xlsx` (лист «Данные», ожидаемые заголовки), но не произвольные Excel-шаблоны.
- Выбранная дата фильтрует записи **каждого** участка; связанный расчёт использует только партии, находящиеся в данном периоде. Это явно более консервативная логика, чем считать обеспеченность на основании строк вне выбранного периода.
- CSV содержит незаверенные записи с причинами; их значения **не включаются** в проверенные агрегаты. Нулевой факт допускается, отсутствие факта — нет.
- База работает в одном экземпляре на локальном компьютере. Для реальной эксплуатации потребовались бы авторизация, управление пользователями, история изменений с авторами, API-схемы, резервные копии, продуктовые правила контроля качества и дополнительные интеграционные тесты.

## Почему такая архитектура

Цель теста — демонстрация **работающей** системы с безопасной передачей данных между участками, а не сложная инфраструктура. SQLite решает требование долговечности после перезапуска; сервис на стандартной библиотеке Python независим от сети и внешних пакетов; клиентское приложение показывает все нужные этапы наглядно. Такой вариант можно объяснить на собеседовании и легко расширить по мере роста требований.

## Continuous Integration

GitHub Actions runs Python syntax checks and regression tests on every push and pull request. The application doesn't require network access or Python dependencies. SQLite database files are ignored by Git.
